Template, not built for a specific business

A refund decision should point to an actual repair record, not a phone call.

A customer loses money in a coin- or card-operated machine, reports it, and then the outcome depends on whoever answers the phone: approved, denied "after review," or left waiting weeks with no reference number and no way to check status. This page shows a small, working tool that closes that gap: a resident-facing request form that checks a real per-machine downtime and repair log the moment a request comes in, an automatic reference number and expected turnaround either way, and a building-level dashboard that flags a chronically-failing machine before it racks up a fifth complaint.

Everything below is fictional. When this gets built for a real operator, the machine log is fed by whatever the service team already uses to track repairs, and the refund decision logic is tuned to that business's own policy, not invented here.

How this gets built for real

The matching rule is a starting point, not policy. "A repair logged in the last 14 days auto-approves" is a simple stand-in; a real build encodes the operator's actual refund policy and can route ambiguous cases to a person instead of auto-deciding.
The machine log needs to be where the service team already works. A real build pulls repair events from whatever ticketing or dispatch tool technicians already use, rather than asking them to type into a second system.
The chronic-machine flag is a starting threshold. Three reports in a rolling window is a reasonable default to surface a problem machine early; a real build would tune that threshold against actual complaint history.
