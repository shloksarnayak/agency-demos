A repeat visit that never fixed anything should not restart from scratch

Many field-service businesses take a request through a web form or a shared inbox, dispatch someone, and hope it gets logged. When a fix doesn't hold, the customer calls back, describes the same problem again, and the case effectively starts over with no record that this is the third truck roll for the same issue. This page shows one small, working tool that fixes that: an internal queue where each request is a ticket with a stage (received, dispatched, visited, resolved and verified), an automatic flag when a ticket sits too long in one stage, and a repeat-visit counter so a case that keeps coming back surfaces instead of blending into the queue as if it were new.

Everything below is fictional. When this gets built for a real business, the office view reads from whatever already takes the request (a web form, a shared inbox, a dispatch app), and the overdue/repeat-visit thresholds and any automatic status message are set to match how that business actually operates.

How this gets built for real

The overdue and repeat-visit thresholds shown here are illustrative. A real build uses whatever cutoff the business actually treats as too long, and whatever visit count it considers a pattern worth escalating.
The status message here is only a log entry. A real build sends it as an actual text or email through the business's existing channel, not a new system the customer has to learn.
The reference code is whatever the business already hands out. A real build reads from an existing ticket, work order, or confirmation number instead of inventing a new one.
